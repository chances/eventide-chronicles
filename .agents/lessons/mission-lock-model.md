# Mission Lock Model

How the mission mutex is modeled and checked, so that refactoring the mission triggers cannot change the behavior they have today. The behavior baseline is [lib/fixtures/thread-graph.json](../../lib/fixtures/thread-graph.json), generated by [tools/thread-graph](../../tools/thread-graph/graph.ts) and compared by [lib/thread-graph.test.ts](../../lib/thread-graph.test.ts). The plan is [mutexes-for-missions.md](../plans/mutexes-for-missions.md).

## Toolchain

- The parser is the `tree-sitter-gta3` grammar built to wasm, loaded with `npm:web-tree-sitter`. `SBL_WASM` in `.env` points at the wasm. Rebuild it after a grammar change with `TREE_SITTER_WASI_SDK_PATH=<wasi-sdk folder> tree-sitter build --wasm -o tree-sitter-gta3.wasm`. The CLI's own wasi-sdk download failed at 98% after about 160 seconds, so download the archive with `curl` and point the variable at the extracted folder.
- Lean 4.35.0 is installed with elan at `D:\Users\enigm\Lean`. Run it with `ELAN_HOME=D:\Users\enigm\Lean` and `D:\Users\enigm\Lean\bin\lean.exe <file>`. The folder is not on `PATH`.
- Never use `decide +kernel`. One run on a behavior model exhausted memory (over 95% of the total), crashed every other app, and made Windows kill the user session. See "What Kernel Decide Does" below. Run Lean with `-M <megabytes>` and `-T <allocations>`, and shrink a model that `decide` cannot finish instead of raising a limit.
- Label references are matched without regard to letter case, as the compiler does (`:BUS` and `@Bus`, `:INTRO_1455` and `@Intro_1455`).

## What Kernel Decide Does

Sourced from the [Lean tactic reference](https://lean-lang.org/doc/reference/latest/Tactic-Proofs/Tactic-Reference/), [lean4#5665](https://github.com/leanprover/lean4/pull/5665), [lean4#4113](https://github.com/leanprover/lean4/pull/4113), [lean4#13956](https://github.com/leanprover/lean4/pull/13956), [lean4#10258](https://github.com/leanprover/lean4/issues/10258), and a Lean Zulip thread on heartbeats.

- `decide +kernel` reduces the `Decidable` instance in the kernel instead of the elaborator. The kernel ignores transparency, so it unfolds every definition, and it reduces once instead of twice.
- Plain `decide` reduces in the elaborator first, then the kernel rechecks the result. A plain `decide` that finishes also reaches the kernel; the earlier plain `decide` runs here stopped at the elaborator's heartbeat limit before getting that far.
- `maxHeartbeats` has reached the kernel since lean4#4113. A heartbeat counts small allocations (in thousands), not memory, so a computation that holds a few large objects can use much memory without reaching the limit.
- The kernel's recursion depth is bounded by `maxRecDepth` times 16 (lean4#13956). The prototype sets `set_option maxRecDepth 20000` for the rest of the file.
- `Prog.eval` evaluates `b.eval k` inside a lambda over each outcome of `a`. Nothing in the sources says the kernel shares that work, so the cost may multiply with the number of outcomes. This is a reading of the code, not a measurement.
- `lean -M` and `-T` are the `max_memory` and `timeout` options. They were broken in Lean 4.19 to 4.22 and fixed in 4.23 (lean4#10258). No source found says whether `-M` stops a kernel reduction.
- Not established: which of these caused the exhaustion. The run was not repeated, because a repeat risks the session. `native_decide` was not involved in the crash, and nothing found says it is unsafe here.
- `native_decide` on the three INIT theorems that plain `decide` could not finish (`init_same_with_tutorial_death`, `init_extension_is_only_narration_death`, `init_rewritten_starts_after_release`) ran to exit 0 with no errors, inside a Windows job object capped at 3072 MB of 16327 MB total and a 180 second timeout. The cap was first shown to work: a deliberate allocator got `OutOfMemoryException` at a 512 MB cap. The peak memory of the Lean run was not measured.
- Capped runner: `deno task --cwd tools/flow-model capped [--cwd=<dir>] <memoryMB> <timeoutSeconds> <command> [args...]` ([capped.ts](../../tools/flow-model/capped.ts)). It creates a Windows job object through Deno FFI, sets `JobMemoryLimit` with the limit flags `JOB_OBJECT_LIMIT_JOB_MEMORY` (0x200) and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (0x2000), assigns the child to it, and kills the child at the timeout (exit code 124). It does not rely on `lean -M`. `ELAN_HOME` comes from `.env`. Its tests (`deno test --allow-ffi --allow-run tools/flow-model/capped.test.ts`) show a command inside the limit keeps its exit code, an allocator past a 512 MB limit is stopped before the timeout, and a long-running command is killed at the timeout.
- Check the model: compile the module with `deno task --cwd tools/flow-model capped --cwd=../.. 3072 120 <lean.exe> -o dist/lean/MissionLock.olean lib/mission-lock.lean`, then run `lib/mission-lock.generated.lean` the same way with `LEAN_PATH` set to the absolute `dist/lean` folder. Run in full, the second step takes about 6 seconds.

## Prototype Result

A throwaway model of the `Star` trigger, the `Cop` mission, and the `HOT` trigger, with one lock bit, one program counter per process, and one `wait`-delimited run per step. Lean checked each statement with `decide`. The lock table below checks the protocol only; the behavior table compares a rewritten thread with its baseline.

| Statement | Result |
|---|---|
| At most one holder, and the lock bit is set exactly when a process holds it | Proved over 20 reachable states |
| Every reachable state has an enabled step, or every process is done | Proved |
| Depth 8 reaches no state that depth 7 missed | Proved, so the search is exhaustive |
| The same protocol with the test removed from the acquire | Unsafe, 39 reachable states |

Behavior flow of `INIT`, the opening (mission 0). A thread is a small program of effects, choices for free guards, and loops; the lock effects are removed before two programs are compared (126 visible runs for the baseline, 138 for the rewrite that also handles death in the narration). Cop and the package threads are not yet modeled.

| Statement | Tactic | Axioms |
|---|---|---|
| No death: rewrite and baseline have the same visible runs | `decide` | `propext` |
| Death or arrest while the tutorial shows: same visible runs | `native_decide` | `propext` and one native axiom |
| Holding the lock through the narration adds only death before the tutorial | `native_decide` | `propext` and two native axioms |
| No thread starts while the lock is held | `native_decide` | `propext` and one native axiom |
| Swapping two tutorial effects is caught | `decide` | `propext` |

## Flow Model Pitfalls

- The first full run of the generated file hit a 300 second timeout, and so did the second, after the trigger search was rewritten, so the trigger search was not the cause. The Lean trigger search now indexes the reachable states once and builds the traces one effect level at a time, as the TypeScript side does (Star alone: 33 states, 13 traces, about 3 seconds); the old depth-first search was never timed on its own.
- Death, arrest, and countdown guards are exit atoms (`wasted`, `timerOut`, and their negations) that read three sticky flags in the run state. Enumerating every effect trace of the baseline `Cop` or `Intro` at bound 40 exhausts a 1500 MB Deno heap (`deno task spec measure Cop 12` finishes in 296 ms with 3 traces). `endings` in `lib/mission-lock.lean` and `endingDepths` in `tools/flow-model/program.ts` find the fewest effects to each ending without listing traces; the generated file states the result (`introBound`, `copBound`).
- A list-based search of the lock protocol is fine for the correct protocol (1024 states for 7 processes, under 5 seconds) but not for the broken variants, so those are checked with 3 processes.
- "A held lock only waits" is wrong: every run starts with the `script_name` effect, and `HOT` restarts itself when the player is dead. The property is that no run contains a launch or its preparation (`commitPrefixes` in `tools/flow-model/config.ts`).

## Architecture Decisions

| Question | Decision | Reason |
|---|---|---|
| How the fixture becomes Lean | A Deno generator reads `lib/fixtures/thread-graph.json` and emits the per-process segment tables as `lib/mission-lock.generated.lean`. The protocol semantics and properties are hand-written in `lib/mission-lock.lean`, which imports the generated file. | One source for the process programs. Hand-written copies drift from the sources. |
| State type | The lock bit `$MissionLocked`, the grant bit `$MissionLockGranted`, and one program counter per process, numbered by `wait`-delimited segment. | These are the only globals the protocol reads or writes. |
| Step relation | One run of one process between two yields. Any process may run next, with no fairness assumed. | A GTA thread runs until it yields, and every round-robin order is one of the interleavings. Starvation freedom is not required. |
| World abstraction | `Player.CanStartMission`, location checks, `Player.IsPlaying`, and the other guards are free inputs chosen at each step. Death and arrest are an extra enabled step for a mission process that jumps to its handler, which re-locks first. | The proof then covers every world, not the ones a play test happens to reach. |
| Properties | Safety: at most one process between acquire and release, and the lock bit is set exactly then. Deadlock freedom: every state has an enabled step or every process is done, and a holder always has a path to its exit. Release only after cleanup: the lock reads `false` only when no process is in a held or cleanup segment. | These are the three properties the plan's constraints name. |
| Behavior preservation | Each trigger and mission is a program of guards and effects, taken from the fixture. For every valuation of the free guards, the rewritten program has the same ordered effects as the baseline program when the lock is free, and yields with no effect when it is held. The only allowed additions are the lock test, the acquire, and the release. Lean proves this refinement for each of the seven triggers, the mission 0 relaunch, and the Fairy launch. | The refactor must not change the order of fades, control locks, waits, or launches, or which mission starts. The lock properties alone would pass a trigger that launched the wrong mission. |
| Frozen baseline | `lib/fixtures/thread-graph.json` is copied once to `lib/fixtures/thread-graph.baseline.json` before Task 4 edits any source. The baseline copy is never regenerated; the live fixture follows the sources. | The refinement needs the old programs after the sources have changed. |
| Tie to the Deno flow test | Both read the same fixture. The flow test regenerates the Lean file and fails when it differs from the committed one. Lean runs as its own command, because the toolchain lives outside the repository. | The proof is then about the programs the flow test checks. |

Bounded search is exhaustive here because the state space is finite and the search reaches a fixed point. Task 3 repeats the fixed-point check on the real model.

## Baseline Findings

- `Tools` and `Hell` have a `script_name` and no start site. `DEFINE MISSION 10 AT @Heaven` names a label that does not exist.
- `lib/debug.txt` is included by `main.txt` and is written by `deno task build`, so a clean checkout lacks it.
- `$ONMISSION` appears 5 times in `lib/threads/ringu.txt` and 5 times in `lib/threads/bath.txt`; Task 8 lists six sites for each.
- Line numbers in the plan have drifted from `main.txt` by two lines at `HOT` (now 241) and the `INIT` relaunch (now 1733).
